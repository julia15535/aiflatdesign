# Стиль документации

Правила как писать файлы в `.memory_bank/`. Цель — документация-справочник, к которой возвращаются через месяц и сразу понимают суть.

## Главное правило

Объясняем **ЧТО и ЗАЧЕМ**, не **КАК именно**.

- ✅ "Бот хранит память диалогов в оперативке. Минус: при рестарте незаконченные диалоги теряются — это сознательно, для MVP проще, чем заводить отдельную базу."
- ❌ "В `bot.py` line 245 создаётся объект `dp = Dispatcher(storage=MemoryStorage())` где MemoryStorage из `aiogram.fsm.storage.memory`..."

**Почему**: код меняется, line numbers съезжают, конкретные имена устаревают. Концепции и причины остаются.

## Размеры

| Тип файла | Целевой размер | Что значит "слишком много" |
|---|---|---|
| Файл в `domain/`, `ai/`, `bot/` | 150-400 строк | >500 — разбить по подтемам |
| `CLAUDE.md` (manifest) | 200-600 строк | можно больше, это центральный документ |
| План | 50-150 строк | >200 — наверное лучше 2 плана |
| Файл в `_claude/` | 30-200 строк | короче лучше — это quick-reference |
| Auto-memory pointer | до 30 строк | каждый файл = 1 концепция |

## Что МОЖНО

- ✅ Таблицы сравнений (до 5 строк обычно достаточно)
- ✅ Короткие списки буллетами
- ✅ Цитаты конфигов, форматов JSON, шаблонов промптов
- ✅ Ссылки на соседние файлы памяти и на код
- ✅ Короткие примеры кода (1-5 строк) если без них непонятно
- ✅ Описание трейд-офф'ов (что выиграли / что потеряли при выборе)
- ✅ "Что НЕ работает" — типичные грабли

## Что НЕЛЬЗЯ

- ❌ Длинные примеры кода (>15 строк) — для этого есть сам код
- ❌ ASCII-зарисовки UI экранов
- ❌ Полные реализации функций / классов
- ❌ Пошаговые инструкции с конкретными командами на каждый чих
- ❌ Дублирование с другим файлом — ссылаемся, не копируем
- ❌ Английские термины без перевода если есть русский эквивалент
- ❌ Эмодзи в технических файлах кроме ✅ ❌ ⚠️ для разметки

## Структура файла

```markdown
# Заголовок

1-2 предложения что это и зачем.

## Раздел 1

Текст. Таблицы. Короткие списки.

## Раздел 2

...

## Связанные файлы

- `path/to/another.md` — что там
```

Заголовок 2-го уровня (`##`) — основные разделы. 3-го (`###`) — подразделы если нужно. 4-го (`####`) — почти никогда.

## Тон

- Объясняем как взрослому коллеге который не знает этой части проекта
- Без поучительности ("обязательно убедитесь что...")
- Без излишней осторожности ("возможно, могло бы быть так что..." → просто "так")
- Без слов-наполнителей ("в принципе", "как известно", "довольно-таки")

## Для общения с пользователем (не разработчик)

В **чате** с пользователем — ещё проще: без английских терминов, всегда раскладывать на плюсы/минусы/риски. См. `auto-memory feedback_simple_language.md`.

В **файлах памяти** — технические термины допустимы (это для меня и других помощников). Но всё равно объясняем смысл коротко.

## Когда обновлять документацию

- При архитектурном изменении (новый stage в pipeline, изменение state machine) — обновить соответствующий файл в `domain/` или `ai/`
- При новом найденном "грабле" — записать в `ai/fail_patterns.md` или `_claude/DECISIONS.md`
- При новом понимании "почему именно так" — добавить в нужный файл, не плодить новые
- При завершении плана — статус и перенос в `completed_plans/`

## Антипаттерн: переписывание

Файлы памяти **дополняем**, не переписываем. Если что-то противоречиво — оставляем оба варианта с датами, потом убираем устаревшее.

Если файл больше не актуален — удаляем целиком, не оставляем "// deprecated" в нём.
